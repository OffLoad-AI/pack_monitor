# Results

Measured on a synthetic corpus of **40 products, 125 artwork versions, 2,125
marketplace-transformed listing images**, generated by `tools.corpus` with seed
`20260101`. Ground truth is exact: every scraped file records the artwork version it
was derived from, and the pipeline never sees that record.

Reproduce with the three commands in the [README](README.md), then
`python -m tools.accuracy --corpus ../data/corpus`.

---

## Headline

| Measure | Result |
|---|---|
| Version identification accuracy | **99.20%** (2,108 / 2,125) |
| False alarms — approved artwork reported stale | **0** of 782 |
| Accuracy where a version was identified | **100.00%** (2,108 / 2,108) |
| Images the system declined to identify | 17 (0.80%) |

The second and third rows matter more than the first. **Every image the system
identified, it identified correctly.** The 17 failures are all refusals —
`UNKNOWN_IMAGE` — not wrong answers. Not one listing serving approved artwork was
reported as stale, at any quality or size.

Quality barely matters. That is the expected result and a good sign: the method
keys on structure that survives compression, not on exact pixel values. The spec's
bar of >98% at q≥75 is met with margin at every quality, including q60, which is
below the bar entirely.

## Accuracy by match method

| Method | Share of run | Accuracy |
|---|---|---|
| `HASH_EXACT` | 125 | 100.00% |
| `PIXEL_DIFF` | 35 | 100.00% |
| `REGION_CHECK` | 1,948 | 100.00% |
| `NONE` (declined) | 17 | — |

`PIXEL_DIFF` resolves only 35 images, and that is not a defect — it is the spec's own
premise confirmed. Two versions differing by one number are ~99.9% identical
globally, which is below the noise floor of JPEG compression, so whole-image
screening *cannot* separate them and correctly hands them to the region check. It
fires only where versions differ grossly, such as a palette shift. The
discriminating-region check does the real work, and gets it right every time it
commits.

## Where the approach breaks down

**800×800 with letterbox padding, when the only difference between two versions is
one number.**

The chain is mechanical:

1. The marketplace pads the 1500px artwork to 1800px, then resizes the result to
   800px. The artwork now occupies 667 pixels, and the padding boundary falls at
   66.67 — not on a pixel.
2. Locating that boundary is what sets the scale for the whole comparison. Even
   with sub-pixel edge refinement it lands within about 0.1%, which is a residual
   displacement of roughly a pixel at the far edge of the image.
3. A nutrition value at 800px is a glyph about 10px tall with 1.5px strokes. A
   pixel of residual misregistration is a large fraction of that.

At that point a changed digit and a compression artefact are genuinely comparable in
magnitude, and the ranking between two candidate versions becomes close to a coin
toss. Measured directly: on images the system declines, the best-scoring candidate is
correct only **62.5%** of the time. On images it accepts, it is correct **100%** of
the time. The margin gate is separating those two populations, which is exactly its
job.

**This is the boundary the photograph fallback track needs to take over.** Not
"low quality" — quality is nearly irrelevant. Specifically: heavily downscaled
listings where the artwork does not fill the frame.

### What would move that boundary

- Requesting the marketplace's largest available asset rather than the thumbnail.
  A 1000px image is already at 100%; the cliff is entirely below that.
- Comparing at the region level in the *reference's* resolution by re-fetching a
  higher-resolution crop, where the marketplace exposes one.
- The photograph track (`pipeline/fallback.py`), which does not depend on pixel
  registration at all and is the honest answer for anything the primary track
  refuses.

## Calibration and the noise floor

From `python -m tools.calibrate --corpus ../data/corpus`, over 23,040,000 unchanged
pixels and 43,363,639 pixels inside known edit regions, across 192 image pairs.
Chart: `calibration/noise_floor.png`.

| | Luma | Chroma |
|---|---|---|
| Unchanged, p50 / p99 / p99.9 | 0 / 10 / **89** | 1 / 8 / **29** |
| Inside a real edit, p50 / p90 / p99 | 5 / 13 / 83 | 7 / 11 / 84 |
| Calibrated threshold (p99.9 of unchanged) | **89** | **29** |
| Separation margin (changed p99 − unchanged p99.9) | **−6** | **+55** |

Three things in this table are worth stating plainly.

**Luma and chroma needed separate thresholds.** Their noise floors differ by 3×. A
single threshold set from the luma floor is blind to a palette change: a 15° hue
rotation moves chroma by ~10 and luma by ~5, so it would sit far below an 89-unit
bar and register as no change at all. Splitting them is what makes cosmetic palette
drift detectable.

**The luma separation margin is negative.** The upper tail of unchanged luma
overlaps the upper tail of real edits. At the pixel level, on the hardest images,
compression noise and a real edit are not separable — the calibration tool prints a
loud warning saying so. The system still reaches 99.2% because identification never
depends on that absolute threshold: Stage 4 ranks candidate versions *against each
other* inside the same regions, where both candidates carry the same noise and the
difference between them is the signal.

**The noise floor is strongly size-dependent, and the pooled number hides it.** Per
image, the 99.9th-percentile luma difference has a quartile spread of 19 / 80 / 102.
The easy quarter of the corpus is five times cleaner than the hard quarter. One
global threshold is a compromise across a population that is not homogeneous;
per-size-class thresholds would be a reasonable next step on real data.

## Determinism

Two runs over identical input produce byte-identical findings, excluding row ids and
timestamps — verified by `test_determinism`, which compares verdicts, severities,
match methods, confidences, matched versions and every region box, field, value and
signature. `test_determinism_is_independent_of_worker_count` additionally confirms
results do not depend on how work was divided between processes.

Nothing in the pipeline samples randomly, and every stage is a pure function of the
input bytes. Where a tie is possible — two byte-identical artwork versions under
different labels — it is broken deterministically and in the direction that avoids a
false alarm.

## Cache behaviour

Re-running identical input serves 100% of images from the previous run's results.
The cache key is the source path plus the file hash **plus the product's current
approved version**: unchanged bytes are only safe to skip while the question is also
unchanged, and approving new artwork must re-open every listing for that product.

## Throughput

2,125 images in 134 seconds on 16 cores — roughly **16 images/second**, peak RSS
405MB. Extrapolating to the spec's scale of ~15,000 images, a monthly run is about
16 minutes.

Two things bound this rather than raw compute. Worker processes are started with
`spawn` rather than `fork`, which costs about a second up front but is not optional:
the pipeline has already used OpenCV by the time a run starts, and forking a process
with a live thread pool deadlocks the children silently. And each worker holds a
small LRU of decoded reference artwork, capped because caching every version a
worker touches costs several hundred megabytes per process — with one worker per
core that is the difference between a slow run and an out-of-memory kill.

## Honest caveats

- **The corpus is synthetic.** Its ground truth is exact, which is an advantage, but
  its artwork is rendered by the same code that edits it. Real packaging has
  photography, gradients, foil, and text that the renderer does not produce.
- **The margin gate was tuned on this corpus.** The value (1.12) was chosen by
  measuring where the ranking stops being reliable, but it was measured here and
  would need re-deriving against real listings. The method for choosing it — the
  tightest gate that produces zero false alarms — is what should carry over, not the
  number.
- **Severity comes from the corpus, not from OCR.** `field_key`, `old_value` and
  `new_value` are supplied by ground truth and matched to detected regions by box
  overlap. In production those come from OCR, which will be its own source of error.
- **The photograph track is a stub.** Anything not derived from the brand's own file
  returns `UNKNOWN_IMAGE`. The 17 refusals here are all genuinely our own artwork,
  so the corpus does not yet test the case that module exists for.
